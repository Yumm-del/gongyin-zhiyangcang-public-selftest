# 如何复核这个案例

本说明对应2026-10-10展示包。先把文件完整解压；保留`consulting-case/`下的目录结构。历史证据保存在`evidence/`，新执行结果写入独立目录，不覆盖历史记录。

## 1. 复算公开问卷汇总

需要Python 3，无第三方依赖。在展示包根目录执行：

```powershell
python consulting-case/scripts/verify-survey.py
```

脚本读取`data/public-summaries/`中的两份公开报告快照，提取题目、选项人数和有效填写人次；检查单选合计、选项人数与显示比例，复算关键分母及多选逻辑边界。结果保存在`consulting-case/reproduced/问卷公开统计-核验结果.json`。

应看到：探索题项15、补充题项24，其中选择题表合计35；开户者中未缴存为38/54；全样本为38/155；补充问卷判断阶段49人、操作阶段32人；操作阶段与步骤需求重合范围为0至30人。输出应与[归档结果](evidence/问卷公开统计-核验结果.json)一致。

该执行验证归档快照的算术；不会连接问卷星，也不会获取逐条答卷。公开报告后续变化不会自动改变这次快照。

## 2. 检查商业测算

打开[商业测算Excel](models/养老金咨询案例-商业测算-v1.xlsx)，在“测算与敏感性”保留“原方案情景”：

| 参数／结果 | 原情景 |
| --- | --- |
| T、B每臂人数 | 50,000 |
| T − B首缴率差 | 0.04个百分点，即0.0004 |
| 单位增量贡献 | 200元 |
| 渠道成本 | 5,000元 |
| 人工成本 | 5,000元 |
| 建设摊销与运维合计 | 3,000元 |
| 增量客户／贡献 | 20人／4,000元 |
| 净值／单位贡献盈亏平衡点 | −9,000元／650元 |

复算：`50,000 × 0.0004 × 200 − 13,000 = −9,000`。变动成本结构保持原假设时：`净值 = N × (0.0004 × 200 − 0.20) − 3,000`。

“拆分示例”使用单独的90天教学假设，与200元原情景不同。B−A输入待核，不应直接填入T−B结果。底稿已保留公式与计算值；本展示包没有另外宣称通过Microsoft Excel本机验收。

## 3. 再执行Alpha本地检查

随附`prototype/alpha-v3.4/`中的页面、引擎和原测试文件来自已验证源码包。`tests/review-runner.cjs`是归档再执行时使用的运行器：仅适配两处Git元数据，并保存原有下载证据与截图，浏览器动作和原断言不变。

已验证环境：Node.js v24.19.0、Playwright 1.62.1、Chromium 151.0.7922.34。重新安装依赖需要网络。在展示包根目录执行：

```powershell
cd consulting-case/prototype
npm install
npx playwright install chromium
node alpha-v3.4/tests/review-runner.cjs
```

`package.json`固定Playwright版本。第一条进入检查目录，随后安装依赖和浏览器；最后一条仅运行本地页面上的固定虚构案例，不接入银行系统，也不提交公开问卷。

通过时输出`six-screen Alpha and auxiliary checks: PASS`，退出码0，新检查记录与截图保存在`consulting-case/prototype/tmp/demo2-alpha-qa/`。检查包括输入边界、税差固定算例、暂缓保护、许可撤回、最少信息、跳转与模拟账务分离、投入判断和桌面／手机布局。

历史记录仍是[evidence中的归档版本](evidence/Alpha-v3.4-复核检查记录-20261010.json)，其时间戳与本次运行不同属于正常情况。新运行中的`recordedSourceCommit`引用源码包原记录，不表示展示包当前Git提交；`nativeGitWorktree:false`明确说明这是源码快照。

该执行不会重测在线GitHub Pages。若改动原型，应保存新的源文件指纹和检查结果，不能沿用旧记录作为新版本通过证明。
